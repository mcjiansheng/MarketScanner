# 超市扫描采样间隔评估

本文评估当前超市扫描功能是否需要缩小扫描时间间隔，并从 RTAB-Map 算法链路、iPhone Pro 系列性能、LiDAR 有效范围、人类移动速度、内存与存储压力、二维地图生成质量等角度给出技术结论。

## 结论

不建议把默认扫描间隔直接缩到“越快越好”。当前 App 的 `Update Rate` 默认值是 `1 Hz`，即约每秒向 RTAB-Map 添加一个新节点；可选项已经包含 `0.5 Hz / 1 Hz / 2 Hz / 3 Hz / 4 Hz / 5 Hz / Max`。在超市长距离扫描场景中，默认 `1 Hz` 是稳定优先的保守值，但对走廊、货架通道、转角和价签定位来说略偏稀疏。

推荐路线是：

```text
默认值：保持 1 Hz，保证老设备和长时间扫描稳定。
超市扫描推荐值：2 Hz，作为现场扫描的优先配置。
高质量短分段或慢速扫描：可试 3 Hz。
不建议默认使用：4 Hz、5 Hz、Max。
```

如果要修改产品默认行为，更合理的做法不是把全局默认值从 `1 Hz` 直接改成高频，而是为“超市扫描模式”单独设置推荐采样策略：进入超市扫描时提示或自动应用 `2 Hz`，同时保留用户回退到 `1 Hz` 的能力。

## 当前实现中的扫描间隔

项目里有两个容易混淆的“频率”概念。

第一个是 RTAB-Map 节点更新频率。iOS 设置项 `UpdateRate` 会写入 `Rtabmap/DetectionRate`：

```text
app/ios/Settings.bundle/Mapping.plist
UpdateRate DefaultValue = 1
可选值 = 0, 5, 4, 3, 2, 1, 0.5

app/ios/RTABMapApp/ViewController.swift
Rtabmap/DetectionRate <- UserDefaults["UpdateRate"]
```

这个值决定“新节点加入地图”的上限频率。它不是 LiDAR 原始深度帧率，也不是 ARKit pose 更新频率。ARKit/相机可能以更高频率提供数据，但 RTAB-Map 只按该频率把帧纳入建图节点。

第二个是超市面积覆盖估计频率。当前 `FloorAreaEstimator` 并没有独立定时器，而是在 `statsUpdated(...)` 回调里调用：

```text
supermarketSession?.updateArea(x: x, z: z)
```

因此手机端二维地图中的 `scan_area_cells.json` 覆盖栅格，本质上跟随 RTAB-Map 节点/统计更新节奏。缩短 `UpdateRate` 间隔会让面积覆盖轨迹更密，但也会让数据库节点、图优化压力、保存频率和内存增长同步增加。

## 算法角度

RTAB-Map 的建图更新不是简单拍照存档。每个节点通常会涉及图像/深度数据保存、特征或扫描数据处理、局部约束、回环候选、图优化统计和数据库写入。当前移动端参数已经做了性能限制，例如：

```text
Rtabmap/TimeThr 默认插入 800 ms
RGBD/LinearUpdate = 0.05 m
RGBD/AngularUpdate = 0.05 rad
Kp/MaxFeatures 默认路径中有 200 等限制
```

在超市 data recorder 模式下，代码进一步关闭部分重型流程，例如全局检索、局部检索、关键点提取，并保留未链接节点，以便更偏向记录数据而不是实时做完整地图理解。这说明当前系统已经意识到“大型区域连续扫描”的瓶颈不是采集不到帧，而是每个节点后续处理和存储都很贵。

缩短间隔的算法收益：

- 轨迹更密，长直通道中的局部姿态采样更连续。
- 面积覆盖插值更可靠，尤其是快速经过转角、端架、窄通道入口时。
- 价签记录附近更容易有近时间节点，后续做价签和地图对齐时误差更小。
- 合并分段时，每段内部有更多重叠证据，理论上有利于后处理修正。

缩短间隔的算法代价：

- 节点数量按频率近似线性增长。
- 回环、优化、数据库写入和可视化负担增加。
- 大型地图中，更多节点并不总是更准确；如果高频帧之间视差小、纹理重复，反而可能增加相似货架通道中的错误匹配机会。
- `TimeThr` 被触发时，系统可能临时遗忘旧图以控制更新时间，极端情况下会让实时状态更不稳定。

所以采样间隔的目标不是最大化帧数，而是让相邻节点之间的空间位移落在“既有足够重叠，又有足够运动基线”的范围内。

## iPhone Pro 系列性能角度

截至 2026 年，iPhone Pro 系列已经覆盖从 iPhone 12 Pro 到更新的 Pro 机型。苹果官方文档确认 LiDAR/Scene Depth 面向 LiDAR 设备，并且当前 Pro 机型规格继续包含 LiDAR Scanner。较新的 Pro 芯片和内存显然更适合高频节点处理，但这个项目的瓶颈不只在 CPU/GPU，也在：

- RTAB-Map C++ 侧节点处理时间。
- 深度、RGB、扫描点、数据库 blob 的内存峰值。
- SQLite/数据库写入。
- 大分段保存、复制、校验、重新打开数据库。
- iOS 前台 App 的可用内存压力和热降频。

因此即使 iPhone Pro 性能较强，也不应把 `Max` 或 `5 Hz` 作为大型超市扫描默认值。短时间演示可能流畅，连续数十分钟扫描时会出现完全不同的热、内存和存储行为。

更务实的判断：

```text
iPhone 12/13 Pro：1 Hz 更稳，2 Hz 需要观察 updateTime 和内存增长。
iPhone 14/15 Pro：2 Hz 通常可作为超市扫描推荐起点。
iPhone 16/17 Pro 及以后：2 Hz 应该较稳，3 Hz 可用于慢速、高质量分段试验。
```

如果后续要做自动策略，可以根据 `updateTime`、可用内存、节点数增长、fastMovement、分段内存增长动态调整，而不是按设备型号硬编码。

## LiDAR 扫描范围角度

苹果公开资料中，LiDAR Scanner 被描述为可测量周围物体距离，范围最高约 5 m；Apple Support 对 iPhone 测量 App 的建议距离是 0.5 到 3 m；ARKit Scene Depth 则是精确但低分辨率的深度图。对超市场景来说，这有几个含义：

- 通道两侧货架通常在 0.5 m 到 3 m 内，是 LiDAR 比较有价值的范围。
- 远端货架、长走廊尽头、反光材料、玻璃门、黑色/高亮包装会降低深度可靠性。
- 高频采样不能扩大 LiDAR 的有效距离，只能在移动路径上增加观测机会。
- 如果操作员走得太快，高频可以增加“经过某个货架面的观测次数”，但不能弥补视角过斜、距离过远或材质不可靠。

当前手机端二维地图生成主要使用 `scan_area_cells.json`，而这个覆盖图由轨迹位置加固定 `scanRadius = 1.25 m` 的圆盘栅格估计，不直接使用每帧 LiDAR 点云边界。因此对“快速预览覆盖范围”来说，1 Hz 已经能通过轨迹插值填补不少空隙；但对未来要从点云/局部栅格生成更真实的 occupied/free 地图来说，2 Hz 或 3 Hz 的节点密度会更有价值。

## 人类移动速度角度

正常室内步行速度通常可粗略按 1.0 到 1.4 m/s 估算。考虑到扫描时需要举手机、避让顾客、对准货架，合理扫描速度应该更低，建议控制在 0.4 到 0.8 m/s。

按不同更新频率估算相邻节点间距离：

```text
0.5 Hz：每 2 秒一个节点
  0.6 m/s -> 1.2 m/节点
  1.0 m/s -> 2.0 m/节点

1 Hz：每 1 秒一个节点
  0.6 m/s -> 0.6 m/节点
  1.0 m/s -> 1.0 m/节点

2 Hz：每 0.5 秒一个节点
  0.6 m/s -> 0.3 m/节点
  1.0 m/s -> 0.5 m/节点

3 Hz：每 0.33 秒一个节点
  0.6 m/s -> 0.2 m/节点
  1.0 m/s -> 0.33 m/节点
```

结合当前 `FloorAreaEstimator` 的 `cellSize = 0.25 m` 和 `scanRadius = 1.25 m`：

- 对纯覆盖面积估计，1 Hz 在慢速扫描时已经够用。
- 对转角、端架、价签定位和后续结构地图，2 Hz 更合适。
- 3 Hz 以上只有在操作员慢速移动、设备较新、分段较短时才有明显收益。

因此，从人的移动速度看，推荐把超市扫描的实际操作目标设为：

```text
移动速度：0.5 到 0.8 m/s
节点频率：2 Hz
相邻节点间距：约 0.25 到 0.4 m
```

这个区间能让相邻帧有足够重叠，又不会把节点数量推到过高。

## 内存、数据库和分段角度

节点频率对内存和数据库增长近似线性放大。假设同样走 10 分钟：

```text
1 Hz -> 约 600 个节点
2 Hz -> 约 1200 个节点
3 Hz -> 约 1800 个节点
5 Hz -> 约 3000 个节点
```

即使超市模式使用磁盘临时数据库，并通过分段保存控制峰值，节点频率提高仍会导致：

- 单位时间内数据库增长更快。
- 更早触发数据库阈值或内存阈值。
- 分段保存更频繁，扫描被暂停的次数更多。
- 本地临时空间和外部复制压力更高。
- 后续合并、二维地图生成和离线处理耗时更长。

这和用户之前观察到的“后续分段变小、扫描效率降低”属于同一类风险：高频采样会让系统更快撞到自动分段阈值。虽然之前已经修复了分段内存基线问题，但如果把节点频率提高过多，仍然会因为真实数据增长更快而更频繁分段。

因此不建议把默认值设到 `5 Hz` 或 `Max`。它们适合诊断、短分段、高质量离线数据采集，不适合默认的大型超市巡检式扫描。

## 对二维地图质量的影响

当前手机端二维地图包主要由覆盖边界组成：

```text
scan_area_cells.json -> occupancy_grid.png / preview.png
price_tags.json -> price_tags.geojson
```

这个方案对节点频率的依赖比真实点云建图低，因为 `FloorAreaEstimator` 会在上一个位置和当前位置之间插值，并在每个位置标记半径 1.25 m 的圆盘。也就是说，1 Hz 不会简单造成覆盖线断裂。

但缩短间隔仍有收益：

- 转角处轨迹更接近真实曲线，二维覆盖轮廓更自然。
- 价签记录与最近节点之间的时间差更小。
- 快速绕过货架端头时，不容易把覆盖区域“拉直”。
- 后续如果从 RTAB-Map 数据库提取局部 grid 或点云，高频节点能提供更多结构观测。

对当前二维预览来说，2 Hz 是收益明显、代价可控的点；3 Hz 以后收益开始下降。

## 建议的技术路线

### 阶段一：不改默认，只形成推荐配置

先在文档和操作流程中建议：

```text
大型超市稳定扫描：1 Hz
一般超市/走廊/货架通道：2 Hz
慢速高质量扫描：3 Hz
诊断或短距离实验：4/5 Hz/Max
```

同时要求现场操作员保持 0.5 到 0.8 m/s 的移动速度，不要快速甩动手机。

### 阶段二：为超市扫描模式设置独立推荐值

如果产品上希望减少用户配置成本，可以在“超市扫描设置”中加入“扫描质量”档位：

```text
稳定：1 Hz
均衡：2 Hz
精细：3 Hz
```

进入超市扫描时只影响超市模式，不改变普通 RTAB-Map App 的全局默认使用体验。

### 阶段三：做动态自适应

后续更理想的方案是动态采样：

```text
updateTime 接近 TimeThr -> 降低到 1 Hz
可用内存低或分段内存增长过快 -> 降低到 1 Hz
fastMovement = 1 -> 提示用户放慢，而不是盲目升频
检测到转角/大角速度/价签采集附近 -> 临时升到 2-3 Hz
长直稳定慢速移动 -> 维持 1-2 Hz
```

这比固定高频更适合大型环境，因为真正需要高频的是转角、端架、狭窄通道、价签附近，而不是每一米平直走廊。

## 推荐验证实验

建议用同一条走廊或货架通道做 A/B 测试：

```text
设备：至少一台较旧 Pro 和一台较新 Pro
路线：直走 30 m，含一个 90 度转角，再直走 20 m
速度：0.6 m/s 左右
频率：1 Hz、2 Hz、3 Hz
记录：节点数、updateTime、数据库 MB、分段内存增长、分段次数、二维预览连续性、点云/走廊直线性
```

判定标准：

- 2 Hz 相比 1 Hz，二维地图转角和价签位置有可见改善。
- 2 Hz 不应显著增加错误回环、卡顿或热降频。
- 3 Hz 只有在质量明显提升且分段次数可接受时才进入推荐。
- 5 Hz/Max 若导致分段明显变频繁或 updateTime 长期接近阈值，应只保留为实验选项。

## 最终建议

当前项目确实有“适度缩小扫描间隔”的需求，但不应无限缩小。对超市扫描来说，推荐把 `2 Hz` 作为实用目标，而不是把全局默认直接改成高频。

最稳妥的产品决策是：

```text
保持全局默认 1 Hz。
在超市扫描模式中推荐或自动应用 2 Hz。
为新款 iPhone Pro 和慢速高质量扫描开放 3 Hz。
保留 4/5 Hz/Max 作为调试或短分段实验，不作为默认。
```

这样可以在地图连续性、价签定位、扫描效率、内存安全和长期稳定性之间取得更好的平衡。
