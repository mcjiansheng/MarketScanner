# 超市扫描项目修改问题、修复方法与功能补充总结

本文总结本次 iOS 超市扫描项目改造过程中遇到的主要问题、原因分析、修复方法，以及新增功能的完成逻辑。重点覆盖中文 UI 本地化、自动分段设置、外部存储导出、大型分段保存闪退、调试提示含义、二维地图辅助数据和分段连续性保护。

## 一、项目目标

本轮改造围绕“大型超市场景扫描”展开。普通房间扫描通常面积较小，单次扫描、单个数据库保存即可满足需求；大型超市扫描则会遇到更明显的工程问题：

- 扫描面积大，RTAB-Map 数据库和缓存持续增长。
- 长时间扫描容易占用较多手机本地存储。
- 单个超大分段在保存、优化或导出时容易产生内存峰值。
- 用户需要把扫描结果保存到外接硬盘或其他指定位置。
- 分段后仍要尽量保持轨迹连续，并能后续合并、查看和生成二维地图包。
- UI 需要符合 iOS 标准本地化：中文系统显示中文，其他语言默认英文。

因此，本次修改不是单点功能，而是一套面向大面积扫描的稳定性改造：

```text
自动分段
  -> 每段先安全保存到 App 沙盒
  -> 写出轻量 sidecar 数据
  -> 立即恢复下一段扫描
  -> 后台复制到用户选择的外部位置
  -> 校验成功后清理本地副本
  -> 后续可合并分段或生成二维地图包
```

## 二、用户看到的调试提示含义

### 1. Mapping Stopped! Optimize Now?

这个提示表示当前扫描已经停止，App 询问是否马上执行图优化和网格组装。

按钮含义如下：

- `Only Optimize`：只进行位姿图优化，不立即生成完整 mesh。
- `Yes`：执行图优化，并继续组装出更完整的 mesh。
- `Save First`：先保存当前数据库，之后再通过菜单执行优化或组装。

在大型超市扫描场景中，不建议在一个非常大的未分段数据库上频繁执行重型优化和组装。更稳定的方式是使用自动分段，让每段尽早落盘，之后再合并或离线处理。

### 2. Loop closure rejected, not enough inliers

示例：

```text
Loop closure rejected, not enough inliers (0/18 < 25).
```

这表示 RTAB-Map 发现了一个疑似回环位置，但几何验证阶段匹配点数量不足，因此拒绝这次回环。

这里的含义是：

- `18`：候选匹配数量。
- `0`：通过几何验证的内点数量。
- `25`：接受回环所需的最低内点阈值。

这不是崩溃，也不代表扫描数据已经损坏。它只是说明这一次“我好像回到了之前的位置”的判断没有足够证据，所以系统没有把它加入图优化。长走廊、重复货架、光照不足、纹理相似、快速移动都可能增加这种提示。

### 3. Recovery

示例：

```text
The previous session (...) was not correctly saved, do you want to recover it?
```

这表示上一次临时扫描会话没有正常关闭或保存。常见原因包括：

- Xcode 调试时直接停止 App。
- App 在保存或导出过程中被系统杀掉。
- 手动杀进程或前后台切换时异常退出。
- 保存阶段发生 native abort 或 SIGABRT。

按钮含义：

- `Ignore`：忽略并丢弃上一次未完整保存的临时会话。
- `Yes`：尝试恢复上一次未正确关闭的会话。
- `Cancel`：取消当前操作，暂不处理。

恢复提示本身是保护机制，不是错误根因。真正需要修复的是导致上一次未正常保存的原因，例如超大分段保存时内存峰值过高、外部路径写入不稳定等。

## 三、中文 UI 与 iOS 标准本地化

### 遇到的问题

最初的中文 UI 修改更接近“硬编码中文”：直接把按钮、菜单和提示文字改成中文。这种方式虽然能让当前界面显示中文，但不符合 iOS 标准本地化逻辑：

- 英文系统也会显示中文。
- 后续增加其他语言困难。
- Storyboard、Swift 字符串和 Settings.bundle 字符串来源不统一。
- 无法正确利用 iOS 的系统语言和 App 语言设置。

### 修复方法

本次改为 iOS 标准本地化结构：

```text
Base.lproj/Main.storyboard
  -> 默认英文 UI 结构

zh-Hans.lproj/Main.strings
  -> Storyboard 中按钮、菜单、标题的简体中文翻译

zh-Hans.lproj/Localizable.strings
  -> Swift 代码中弹窗、Toast、菜单文案的简体中文翻译

Settings.bundle/zh-Hans.lproj/Mapping.strings
  -> 系统设置 App 中 Mapping 设置项的简体中文翻译
```

同时在 Xcode 工程配置中加入 `zh-Hans` 本地化区域，并把 `Localizable.strings` 纳入资源。

### 完成后的行为

现在 UI 逻辑是：

```text
iOS 系统语言或 App 语言为简体中文
  -> 显示中文 UI

其他语言
  -> 使用 Base / English 默认 UI
```

这满足“系统中使用中文时提供中文 UI，其他则默认英文 UI”的要求。

## 四、自动分段设置功能

### 需求

用户希望在设置中手动选择自动分段大小和保存位置。核心目标是避免大型超市扫描时单个数据库过大，并让数据能保存到外部存储设备。

### 新增配置项

App 内的“超市扫描设置”提供以下配置：

- 是否启用自动分段。
- 扫描面积阈值。
- 数据库大小阈值。
- 内存增长阈值。
- 分段前最少节点数。
- 选择保存位置。
- 恢复默认保存位置。

系统设置 App 的 `Mapping` 页面也补充了超市扫描相关阈值。保存位置选择必须在 App 内完成，因为 iOS 需要通过文件选择器授予目录访问权限，不能只靠 Settings.bundle 里的静态设置项完成。

### 默认值调整

为了降低大分段保存崩溃风险，当前默认值改为偏保守：

```text
扫描面积阈值 = 120 m2
数据库阈值 = 700 MB
内存阈值 = 1200 MB
分段前最少节点数 = 30
```

这个默认值的目标不是追求最少分段，而是先保证现场可持续扫描。大型超市扫描中，更小、更稳定的分段通常比一个超大数据库更可靠。

### 自动分段触发逻辑

当前分段满足以下任一条件时会触发保存：

```text
估算扫描面积 >= 用户设置的面积阈值
RTAB-Map 数据库内存 >= 用户设置的数据库阈值
当前分段内 App 内存增长 >= 用户设置的内存阈值
```

同时还要求当前分段节点数达到“分段前最少节点数”，避免刚开始扫描时因为瞬时波动过早切分。

内存阈值使用“当前分段开始后的内存增长”，不是 App 启动后的总内存占用。这样可以避免第一次保存和后台复制后留下的系统缓存影响后续分段判断。

## 五、外部存储导出问题与修复

### 原始风险

用户的真实目标是：大型超市扫描时不要长期占用手机本地存储，而是把每段数据保存到外接硬盘或用户选择的位置。

直觉方案是让 RTAB-Map 直接把数据库保存到外部目录。但在 iOS 上这样不稳定，原因是：

- RTAB-Map 数据库保存由 C++ native 层执行。
- iOS 外接盘、文件提供器、iCloud Drive、第三方网盘目录往往是安全作用域 URL。
- Swift 层可以通过文件选择器获得访问权限，但 native C++ 层直接写这些路径并不总是可靠。
- 文件提供器路径可能在底层有权限、同步、占位文件或延迟写入问题。
- native 保存失败时可能不是普通 Swift error，而是 abort / SIGABRT。

### 修复策略：两阶段保存

最终采用稳定优先的两阶段方案：

```text
1. 当前分段扫描中
2. 达到阈值或用户手动保存
3. 暂停 RTAB-Map 采集线程
4. 把 RTAB-Map 数据库保存到 App 本地沙盒
5. 写出 metadata、价签、轨迹、扫描覆盖栅格等 sidecar 文件
6. 打开新的临时数据库
7. 恢复下一段扫描
8. 后台复制刚完成的 segment 到用户选择的外部目录
9. 校验外部副本
10. 校验成功后删除本地 segment 副本
```

这个方案的关键点是：native 层只写 App 自己的沙盒目录，外部路径复制由 Swift `FileManager` 负责。

### 为什么这个方案更稳定

它把高风险路径隔离开：

```text
RTAB-Map native save
  -> 只面对 App 沙盒路径
  -> 权限和文件系统语义稳定

外部存储写入
  -> 由 Swift 层处理
  -> 可以使用 security-scoped resource
  -> 可以捕获复制失败
  -> 可以校验副本
  -> 可以失败后保留本地数据
```

这样即使外部硬盘拔出、空间不足、文件提供器异常，App 也不会立刻丢失已经保存到本地的 segment。

### 本地存储是否仍会占用

会，但只应短暂占用“当前分段和正在后台复制的分段”。

这是两阶段方案的边界：

- 它不能做到 native 数据库完全不经过本地沙盒。
- 它可以避免所有已完成分段长期堆在手机本地。
- 外部复制和校验成功后，本地 segment 会被删除。
- 如果外部复制失败，本地副本会保留，优先保证数据不丢。

因此，外部存储方案依赖合理分段阈值。分段越小，本地临时峰值越低；分段越大，单次保存和复制压力越高。

## 六、170 平米、约 1700 MB 保存闪退问题

### 现象

用户扫描约 170 多平方米，内存约 1700 MB 后点击保存，App 在导出过程中闪退。Xcode 中可见 `Thread signal SIGABRT` 或停在 `__pthread_kill`。

### 原因分析

`SIGABRT` 是进程主动 abort 的结果。Xcode 停在 `__pthread_kill` 只是系统层面的最终位置，不是根因代码行。结合扫描状态，最可能的问题是保存阶段产生了过高的内存或文件写入压力：

- 单个分段面积过大。
- RTAB-Map 数据库和缓存已经很大。
- 保存时需要 close、flush、copy、serialize 等操作，可能出现短时内存峰值。
- 如果数据库在内存中，保存时压力更明显。
- 如果直接写外部路径，native 层可能因为路径或权限异常 abort。

### 修复方法一：超市扫描强制使用磁盘数据库

普通 RTAB-Map 设置中存在 `DatabaseInMemory` 选项，但大型超市扫描不适合把数据库长期放在内存中。

本次修改让超市扫描正常建图时强制使用磁盘数据库：

```text
超市扫描模式
  -> databaseInMemory = false
```

只有特殊的数据记录模式才保留原设置。这样可以降低长时间扫描和保存阶段的内存峰值。

### 修复方法二：降低默认分段阈值

原先较大的阈值容易让单段增长到接近 1700 MB 甚至更高。现在默认阈值更保守：

```text
面积 120 m2
数据库 700 MB
内存增长 1200 MB
最少节点 30
```

同时加入旧默认值迁移逻辑。如果用户仍停留在旧默认值，例如面积 250、数据库 900、内存 2500，App 会迁移到新的稳健默认值。用户仍然可以手动调高，但默认不再鼓励超大分段。

### 修复方法三：保存前检查本地临时空间

两阶段保存需要本地沙盒先容纳当前 segment，因此保存前增加本地可用空间预检：

```text
预估需要空间 = max(当前数据库 MB, 100 MB) * 2 + 512 MB 安全余量
```

如果本地空间不足：

- 不开始 native 保存。
- 保持当前扫描数据。
- 显示本地化空间不足提示。

这样可以避免保存到一半才因为磁盘不足产生更难恢复的错误。

### 修复方法四：修正 Swift 到 native 的保存桥接

保存路径从 Swift 传给 C++ 时，需要传入稳定的 C 字符串指针。本次修复确保调用 native `save` 时传递的是 `buffer.baseAddress`，而不是 Swift `String` 对象本身。

这个修复降低了路径桥接错误导致 native 层异常的风险。

### 修复后的建议操作

对于大型超市：

- 不建议单段扫描到 170 平米以上再保存。
- 建议先使用默认 120 平米阈值。
- 如果外部硬盘速度较慢，可以进一步降低面积或数据库阈值。
- 保存过程中尽量避免切后台、锁屏或拔出外部设备。
- 若出现恢复提示，优先选择恢复或确认本地 segment 是否已保留。

## 七、输出数据与 sidecar 文件

每个分段不仅保存 RTAB-Map 数据库，也会写出轻量辅助文件，方便后续合并、二维地图生成和价签管理。

典型目录结构如下：

```text
SupermarketSession-YYYYMMDD-HHMMSS/
  segment_0001/
    rtabmap_segment_0001.db
    metadata.json
    price_tags.json
    price_tags.csv
    scan_area_cells.json
    trajectory_samples.json
    trajectory_samples.csv
  segment_0002/
    rtabmap_segment_0002.db
    metadata.json
    price_tags.json
    price_tags.csv
    scan_area_cells.json
    trajectory_samples.json
    trajectory_samples.csv
```

主要文件含义：

- `rtabmap_segment_xxxx.db`：RTAB-Map 原生数据库，是后续优化、合并和重建的核心数据。
- `metadata.json`：分段编号、时间、面积、数据库大小、节点数量等元信息。
- `price_tags.json`：NFC 价签绑定数据。
- `price_tags.csv`：方便表格软件查看的价签导出。
- `scan_area_cells.json`：轻量扫描覆盖栅格，用于手机端快速生成二维覆盖图。
- `trajectory_samples.json`：二维轨迹采样点，用于显示分段轨迹中心线。
- `trajectory_samples.csv`：轨迹数据的表格版本。

这些 sidecar 文件的设计目标是“轻量、可检查、可恢复”。即使大型点云或完整地图需要后处理，手机端也能先快速知道扫描覆盖范围、分段数量、价签位置和轨迹趋势。

## 八、二维地图包生成逻辑

App 菜单中的“生成二维地图包”会读取各分段的 sidecar 文件，生成一个轻量地图目录：

```text
Map2D-YYYYMMDD-HHMMSS/
  map.json
  occupancy_grid.png
  occupancy_grid.yaml
  preview.png
  trajectory_samples.json
  semantic_layers.json
  price_tags.geojson
  quality_report.json
```

当前手机端二维地图主要解决“快速预览”和“现场检查”：

- 查看哪些区域已经扫过。
- 查看分段轨迹是否有明显漂移或折角。
- 查看价签点是否落在合理位置。
- 生成便于后续工具读取的地图描述文件。

需要注意的是，手机端快速二维图不是完整的货架/墙体语义地图。它主要基于轨迹和扫描覆盖栅格生成。要得到更精确的墙体、货架、障碍物占据图，仍建议使用离线工具读取 RTAB-Map 数据库或点云进行更完整的后处理。

## 九、分段连续性与 ARKit 姿态保护

### 问题

分段保存需要暂停、保存、打开新数据库、继续扫描。这个过程如果处理不好，容易造成轨迹在分段边界处突然折角。

另外，ARKit 在 `.limited(.relocalizing)`、`.limited(.initializing)` 或 `.notAvailable` 状态时，如果继续把空 pose 帧送给 RTAB-Map，native 层可能误以为需要重置移动端相机原点。

### 修复逻辑

本次改造包含两类保护：

```text
分段 stop/start
  -> 保留移动端相机原点
  -> 避免新分段第一帧重新定义原点

ARKit tracking 不可接受
  -> 不继续投递空 pose 帧给 RTAB-Map
  -> 避免 native 层 resetOrigin
```

这可以减少长直走廊、来回扫描和分段边界处出现突然折角或分叉的概率。

### 边界

这些修复不能消除所有漂移。以下情况仍可能带来误差：

- 长走廊纹理重复。
- 货架结构高度相似。
- 光照过暗或反光严重。
- 用户移动过快。
- LiDAR 深度缺失。
- ARKit 本身发生缓慢 yaw 漂移。
- 回环检测因匹配点不足被拒绝。

因此，大型超市最终精度仍需要依赖合理扫描路线、足够重叠、适当回环，以及后续图优化或离线合并。

## 十、合并已保存分段

### 问题

分段保存后，用户如果直接点击优化，可能看到 `Optimization failed`。原因是优化入口原本针对“当前打开的数据库”，而不是自动扫描目录中已经保存的多个分段。

分段保存后，当前临时库可能已经是新的空库，而旧分段已经写入：

```text
segment_0001/rtabmap_segment_0001.db
segment_0002/rtabmap_segment_0002.db
segment_0003/rtabmap_segment_0003.db
```

此时对当前空库执行优化，自然会失败。

### 修复方法

优化入口增加判断：

```text
当前图有节点
  -> 执行正常优化

当前图没有节点，但存在已保存分段
  -> 提示用户使用“合并已保存分段”

当前图没有节点，也没有已保存分段
  -> 提示还没有可优化数据
```

同时新增“合并已保存分段”入口，用于把保存到磁盘上的 segment 数据库作为一个独立流程处理。

### 设计意义

这把两个操作语义区分开：

- `Optimize`：优化当前正在打开的图。
- `Merge Saved Segments`：合并已经落盘保存的多个分段。

这样用户不会把“当前空库优化失败”误认为“已保存分段损坏”。

## 十一、失败保护策略

大型扫描中最重要的原则是：宁愿保留更多本地副本，也不要误删未确认写成功的数据。

当前失败保护如下：

```text
本地空间不足
  -> 不开始导出
  -> 保持当前扫描数据
  -> 显示空间不足提示

本地保存失败
  -> 不打开下一段
  -> 提示保存失败
  -> 尽量保留当前状态

sidecar 写入失败
  -> 保留数据库
  -> 提示辅助文件写入问题

外部复制失败
  -> 保留本地 segment
  -> 显示复制失败提示

外部复制成功但校验失败
  -> 保留本地 segment
  -> 显示校验失败提示

外部复制成功且校验成功
  -> 删除本地 segment 副本

删除本地副本失败
  -> 外部副本保留
  -> 本地副本也保留
  -> 提示用户本地清理失败
```

外部副本校验主要检查：

```text
外部副本文件数量 == 本地副本文件数量
外部副本总字节数 == 本地副本总字节数
```

它不是数据库级完整性校验，但足以发现常见的复制中断、漏文件和明显大小不一致问题。

## 十二、用户推荐操作流程

大型超市扫描建议流程：

```text
1. 打开 App
2. 进入设置 -> 超市扫描设置
3. 开启自动分段
4. 使用默认阈值，或根据设备压力调低阈值
5. 点击选择保存位置
6. 选择外接硬盘或本地指定目录
7. 开始扫描
8. 扫描时保持移动缓慢、路线有重叠、尽量形成回环
9. 自动分段触发后等待 App 恢复扫描
10. 后台会复制和清理已完成分段
11. 扫描结束后保存当前分段
12. 使用合并已保存分段或生成二维地图包检查结果
```

如果用户没有选择保存位置，App 会使用默认 Documents 目录，并保留本地 segment。

如果用户选择外部保存位置，App 会把已完成分段复制到该位置；复制并校验成功后，本地 segment 会被清理。

## 十三、验证情况

本轮修改后执行过以下验证：

- `Localizable.strings` 语法检查。
- `Main.strings` 语法检查。
- `Settings.bundle` 相关 plist / strings 检查。
- iOS Debug 真机目标 `xcodebuild` 编译。

编译结果可以通过，但仍有项目既有 warning。当前文档关注的是本轮功能逻辑和稳定性修复，不代表所有历史 warning 都已经清理。

## 十四、仍需注意的风险

### 1. 外接存储不是实时数据库

外接硬盘或文件提供器目录适合保存完成后的 segment，不适合让 native RTAB-Map 直接作为实时数据库写入目标。当前两阶段方案正是为了规避这个风险。

### 2. 本地仍需要临时空间

即使选择外部硬盘，本地也需要容纳当前分段。用户应避免把单段阈值设置得过大，否则仍可能因为本地空间或内存峰值导致失败。

### 3. 超大分段仍不推荐

170 平米、1700 MB 级别的单段已经接近高风险区间。更可靠的方式是用较小分段换取持续扫描稳定性。

### 4. 回环失败不等于数据损坏

`Loop closure rejected` 说明某次回环证据不足。只要扫描仍在进行，它更多是定位质量提示，不是致命错误。

### 5. 恢复提示需要结合前一次退出原因判断

`Recovery` 说明上次会话没有正常结束。若前一次是手动停止 Xcode 或强制杀 App，通常可以按需忽略；若前一次是保存闪退，建议尝试恢复并检查本地 segment。

## 十五、总结

本次改造的核心思路是把大型超市扫描从“单个巨大数据库一次性保存”改成“可配置的小分段、稳定落盘、后台外部导出、可恢复、可合并”的流程。

主要完成点包括：

- UI 改为 iOS 标准本地化，中文系统显示中文，其他语言默认英文。
- 新增超市扫描设置，用户可配置自动分段阈值。
- 支持用户选择外部保存位置。
- 使用两阶段保存，避免 RTAB-Map native 层直接写外部路径。
- 外部复制成功并校验后删除本地 segment，降低手机长期存储占用。
- 大型分段保存前检查本地可用空间。
- 超市扫描强制使用磁盘数据库，降低内存峰值。
- 下调默认分段阈值，避免单段过大导致保存闪退。
- 修复 Swift 到 native 保存路径桥接风险。
- 补充分段 sidecar 文件，支持价签、轨迹、扫描覆盖和二维地图包。
- 加强 ARKit tracking 和分段边界的姿态保护。
- 区分当前图优化和已保存分段合并，减少用户操作误判。

整体上，当前方案不能让外部存储完全取代 App 本地临时目录，但可以保证 RTAB-Map 保存路径稳定，并在外部复制校验成功后清理本地副本。对于大型超市扫描，这是比直接写外接盘更稳健的实现方式。
